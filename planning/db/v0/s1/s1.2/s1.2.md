# Kidney Care — DB Design Plan (v0 / s1 / s1.2)

Date: 2026-07-03

## 1. Summary

Single-field delta on s1.1, discovered while planning the local DB + sync implementation (see `planning/sync/v0/stage-1.md`). To support a DB-trigger-based bootstrap of the `patients` row on signup (chosen over app-side "create if missing" during sync design), `patients.first_name` and `patients.last_name` must stay nullable — the trigger creates the row immediately on `auth.users` insert, before the user has entered any profile info.

## 2. Entities

Unchanged from s1.1, except `patients`:

| Entity | Description | Change from s1.1 |
|---|---|---|
| `patients` | Core patient/account record | `first_name` / `last_name` remain nullable (explicit bootstrap contract) |
| `blood_pressure_readings` | Systolic/diastolic + optional heart rate | No change |
| `blood_glucose_readings` | Glucose value (mg/dL) + context | No change |
| `weight_readings` | Weight value (kg) | No change |

## 3. Key Relationships

Unchanged from s1.1.

## 4. Access Patterns

Unchanged from s1.1.

## 5. Design Decisions

| Decision | Choice | Reason |
|---|---|---|
| `patients.first_name` / `last_name` nullability | Explicitly nullable for signup bootstrap | A Postgres trigger on `auth.users` now auto-creates the `patients` row at signup time so it always exists by the time the app's sync engine runs (see sync plan §7.2 for the trigger + rationale vs. app-side creation). At that moment the user hasn't entered a name yet. App-layer onboarding is responsible for prompting until profile fields are filled in. |

## 6. Open Questions

- Should other currently-nullable profile fields (`date_of_birth`, `sex`, `ckd_stage`) get an explicit "profile incomplete" flag instead of relying on name fields being NULL? Not needed yet at this scope — revisit if profile fields grow.
