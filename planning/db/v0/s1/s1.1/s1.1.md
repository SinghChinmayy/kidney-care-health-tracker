# Kidney Care — DB Design Plan (v0 / s1 / s1.1)

Date: 2026-07-03

## 1. Summary

Scope-reduced revision of s1, focused on shipping a first implementable slice: **patient profile + vitals only**. Vitals are split from s1's single generic `vital_readings` table into one dedicated table per metric (`blood_pressure_readings` incl. heart rate, `blood_glucose_readings`, `weight_readings`), each storing a canonical unit with any conversion handled at the app layer. All other s1 entities (care team, labs, medications, symptoms, diet/fluid, appointments, dialysis sessions, documents, reminders) are deferred to a later stage, not removed from the overall plan.

## 2. Entities

| Entity | Description | Est. rows — launch / 1yr / 5yr |
|---|---|---|
| `patients` | Core patient/account record, unchanged from s1 | scale TBD |
| `blood_pressure_readings` | Systolic/diastolic + optional heart rate | highest-volume table — multiple rows/patient/day |
| `blood_glucose_readings` | Glucose value (mg/dL canonical) + loose context tag | multiple rows/patient/day |
| `weight_readings` | Weight value (kg canonical) | ~1 row/patient/day typical |

All other s1 entities are **out of scope for this stage** — see `../s1.md` / `../s1.dbml` for their design, to be reintroduced in a future stage.

## 3. Key Relationships

- All three vitals tables are 1:N off `patients`, same pattern as s1.
- No relationships between the three vitals tables themselves — each is independent, queried/filtered by `patient_id` + `recorded_at`.

## 4. Access Patterns

| Pattern | Frequency | Index strategy |
|---|---|---|
| Trend/history per metric (BP, glucose, weight) for charts | Highest-frequency read | `(patient_id, recorded_at)` on each vitals table |
| Log a BP/HR, glucose, or weight reading | Highest-frequency write | pk insert only |
| Offline sync — pull changes since last sync | Every reconnect | `(patient_id, updated_at)` on every table |

## 5. Design Decisions

| Decision | Choice | Reason |
|---|---|---|
| Vitals modeling | Split into one table per metric (`blood_pressure_readings`, `blood_glucose_readings`, `weight_readings`) instead of s1's single generic `vital_readings` table | User-requested simplification; each table now has purpose-built typed columns instead of a generic `metric_type` + `value_numeric`/`value_secondary` pair, making queries and client models more direct |
| Blood pressure + heart rate | Combined into one table, `systolic`/`diastolic`/`heart_rate_bpm` all independently nullable | Covers BP-cuff readings (with or without pulse), pulse-only readings (e.g. fitness band), and combined readings, all in one row shape; app layer enforces at least one value group present |
| Units | Store canonical unit only, no per-row `unit` column (`value_mg_dl` for glucose, `value_kg` for weight, mmHg/bpm implicit for BP/HR) | User decision: unit conversion (e.g. mmol/L → mg/dL, lb → kg) happens at the app/logic layer before writing, so the DB never stores mixed units or needs a unit column |
| Glucose context | `context` column added as free text now, not an enum | User decision: field is needed conceptually (fasting/post-meal/etc.) but exact enum values not finalized yet — captured as text placeholder, to be converted to a proper `ENUM` in a later stage |
| Scope | Only `patients` + 3 vitals tables in this stage; all other s1 entities deferred | User-requested simplification to ship a first implementable slice; profile table itself kept at full s1 field set (not trimmed) since only the vitals modeling needed simplifying |
| SpO2 / temperature | Dropped from this stage (were part of s1's generic `vital_metric_type` enum) | Not mentioned in the requested 3-table split; can be added later as additional per-metric tables following the same pattern established here |

## 6. Open Questions

- **Glucose `context` enum values**: to be finalized in a later stage (candidates: `fasting`, `post_meal`, `random`, `bedtime`) and migrated from free text to a formal `ENUM`.
- **SpO2 / temperature vitals**: not included in this stage — revisit if/when needed, following the same one-table-per-metric pattern.
- **Deferred entities re-introduction order**: care team, labs, medications, symptoms/diet, appointments, dialysis, documents, reminders all still need to be scoped into an implementation stage — order/priority not yet decided.
- All open questions from `../s1.md` (caregiver access, soft-delete grace period, RLS policies, `lab_results.test_name` taxonomy, reminders vs. dose-logs) still stand for when those entities are reintroduced.

## 7. Change Log

- **v0/s1/s1.1** (2026-07-03): Scope reduced to `patients` + vitals only, as an implementable first slice. `vital_readings` (generic, s1) replaced by 3 dedicated tables: `blood_pressure_readings` (+ heart rate), `blood_glucose_readings`, `weight_readings`. Removed per-row `unit` columns in favor of canonical units with app-layer conversion. Added free-text `context` field on glucose, to be formalized as an ENUM later. All other s1 entities deferred (not deleted from the overall plan).
