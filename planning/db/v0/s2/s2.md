# Kidney Care — DB Design Plan (v0 / s2)

Date: 2026-11-12

## 1. Summary

Stage 2 ports the useful parts of the archived v1 app into the v2 schema: richer measurement context (BP arm/posture/dialysis day), small metadata additions (patient blood group, glucose `before_meal`, `recorded_by` attribution), and the first real access model. The 1:1 "one patient per auth user" assumption from s1 is dropped: each user still gets a *self* patient at signup, but any user can own or be granted access to many patients through `patient_access` with roles `owner` / `caregiver` / `viewer`. All RLS now goes through one `private.has_patient_access(patient_id, min_role)` check. Access-control writes (create patient, grant/change/revoke) happen only through SECURITY DEFINER RPCs that verify the caller — the v1 self-grant hole is not ported. The design was decided up front (port brief), so the stage skips the interview step.

## 2. Entities

| Entity | Description | Est. rows — launch / 1yr / 5yr |
|---|---|---|
| `patients` (changed) | Patient record. `auth_user_id` now nullable (patients created for someone without an account), still unique. New `blood_group`. | ~1-3 per user |
| `blood_pressure_readings` (changed) | New `arm`, `posture`, `is_dialysis_day`, `dialysis_phase`, `recorded_by` | unchanged (highest volume) |
| `blood_glucose_readings` (changed) | New `recorded_by`; `context` vocabulary gains `before_meal` | unchanged |
| `weight_readings` / `fluid_intake_logs` (changed) | New `recorded_by` | unchanged |
| `patient_access` (new) | (patient, user, role) membership; the only source of authorization | ~1-5 per patient |
| `profiles` (new) | `user_id` → unique `username`, used only for share-by-username | 1 per user who sets a username |

## 3. Key Relationships

- `patients` M:N `auth.users` through `patient_access` (`unique (patient_id, user_id)`). Replaces the implicit 1:1 via `patients.auth_user_id`.
- `patients.auth_user_id` keeps meaning "the account this record describes" (self patient). It is no longer used for authorization; it is immutable from clients.
- `profiles` 1:1 `auth.users` (pk = `user_id`), optional.
- `recorded_by` on the four log tables → `auth.users(id) on delete set null`; set by trigger, not by clients.

## 4. Access Patterns

| Pattern | Frequency | Index strategy |
|---|---|---|
| RLS check on every row read/write | Every query | `patient_access (patient_id, user_id)` unique index; function is `stable` so it is evaluated per row with a cheap index probe |
| "Which patients can I access?" (sync, switcher) | Every sync run | `idx_patient_access_user (user_id)` |
| Per-patient incremental pull | Every sync run × patients | existing `(patient_id, updated_at)` indexes |
| Members of a patient (access screen, "logged by") | Occasional | `patient_access (patient_id, user_id)` |
| Username lookup | Rare (sharing) | `profiles_username_key` unique index |

## 5. Design Decisions

| Decision | Choice | Reason |
|---|---|---|
| Access model | `patient_access(patient_id, user_id, role)`; roles owner > caregiver > viewer | Decided in port brief. Keeps patients table shape; ranks make `min_role` checks trivial |
| RLS shape | Every app-table policy calls `private.has_patient_access(patient_id, min_role)` (SECURITY DEFINER, `search_path = ''`) | One audited check; definer avoids recursive RLS on `patient_access` |
| Read / write split | select = viewer+; insert/update/delete = caregiver+; access management = owner (RPC) | Decided in port brief |
| Writing `patient_access` | No client insert/update/delete policies **and** no table privileges; only SECURITY DEFINER functions write it | v1 let any user insert `(auth.uid(), 'owner')` for any patient → self-granted ownership. Closed by construction |
| Creating patients | `public.create_patient(...)` RPC; client `INSERT` on `patients` revoked | Caller becomes owner atomically; accepts an optional client uuid and is idempotent for the same owner |
| Self patient | Signup bootstrap still creates it and now also inserts the owner row | Keeps v2 onboarding/initial-sync flow working; backfill gives existing users owner rows |
| Owner invariants | Last owner cannot be removed or demoted (owner rows locked `for update`); the self patient's own account can never be removed and only they can change their role | Prevents orphaned patients and people being locked out of their own record |
| Soft delete of patients | Owner-only, enforced by `guard_patient_update` trigger; `auth_user_id` immutable | RLS update policy is caregiver+, column rules need a trigger |
| Revocation | Hard delete of the `patient_access` row | Clients detect revocation by diffing their access list and evict cached data; no tombstone needed |
| Usernames | `profiles.username` `^[a-z0-9_]{3,30}$`, unique; owner-only RLS; lookup through `find_user_by_username` returning `(user_id, username)` only | Share by handle without exposing email or a browsable directory |
| Member list visibility | `list_patient_members` allowed for any member (viewer+) | Needed to render "logged by" and the access screen; returns username + role only |
| `recorded_by` | `before insert or update` trigger: insert → `auth.uid()` (ignores client value); update → keeps old value | Attribution cannot be spoofed or rewritten. Backfill = patient's own user (all historic rows were self-logged) |
| BP context columns | `arm` (left/right), `posture` (sitting/standing/lying), `is_dialysis_day` (nullable bool), `dialysis_phase` (pre_dialysis/post_dialysis, only when dialysis day) | Mirrors v1 semantics with v2 naming (`pre_/post_dialysis` like `weight_readings.dialysis_timing`); all nullable, no backfill |
| Glucose `before_meal` | App vocabulary only; column stays free text | s1.1 deferred a formal enum; adding a CHECK now could reject unknown legacy values |
| Blood group | `patients.blood_group` with CHECK on the 8 ABO/Rh values | Same as v1 |

## 7. Open Questions

- **Invitations**: sharing requires the other person to already have an account and username. Email invites / pending grants are not designed.
- **Ownership transfer UX**: multiple owners are allowed, so transfer = grant owner + leave. No dedicated flow.
- **Patient deletion**: owner may soft-delete via `deleted_at`, but there is no UI and no cascade to `patient_access`.
- **Glucose context enum**: still free text; audit legacy values before adding a CHECK.
- **Medication catalog** remains local-only (out of scope).
- **Rate limiting** of `find_user_by_username` (enumeration by guessing exact handles) relies on Supabase API rate limits only.

## 8. Change Log

- **v0/s2** (2026-11-12): Stage created from the v1 → v2 feature port. Dropped the 1:1 patient/user assumption, added `patient_access` + `profiles`, centralised RLS in `private.has_patient_access`, added BP measurement context, blood group, and server-set `recorded_by`. Resolves the s1 open questions "Caregiver access (future)" and "RLS policies".
